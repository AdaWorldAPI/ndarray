## 3. Feature gating in 3.0.0

- `static_secrets` is still the feature name:
  `/home/user/curve25519-dalek/x25519-dalek/Cargo.toml:59`
  `static_secrets = []` (an empty/marker feature, same as (assumed) 2.0.1).
- `StaticSecret: From<[u8; 32]>` is still available under it — confirmed
  above, `x25519.rs:246-252`, gated on exactly `#[cfg(feature = "static_secrets")]`.
- `EphemeralSecret` in 3.0.0 is a **different, always-present type** —
  `x25519.rs:78` `pub struct EphemeralSecret(pub(crate) [u8; 32]);`, no
  `#[cfg(...)]` on the struct at all (unlike `StaticSecret`/`ReusableSecret`,
  which ARE gated). Its two generation paths:
  - `random_from_rng<R: CryptoRng + ?Sized>(csprng: &mut R) -> Self`
    (`x25519.rs:87-93`) — needs a `rand_core::CryptoRng` implementer. `rand_core`
    is a mandatory (non-optional) dependency of x25519-dalek 3.0.0
    (`Cargo.toml:42`: `rand_core = { version = "0.10", default-features = false }`
    — **no `optional = true`**, unlike `getrandom`/`serde`/`zeroize` immediately
    below it in the same file), but `kx.rs`'s crate (`encryption`) does not
    depend on `rand_core` itself and has no CSPRNG type implementing it —
    `crate::fill_random` is the sole entropy chokepoint, per kx.rs:16-18 doc.
    Still unreachable from `kx.rs` without adding that dependency.
  - `random() -> Self` (`x25519.rs:95-102`) — `#[cfg(feature = "getrandom")]`.
    `encryption`'s `Cargo.toml` enables `x25519-dalek` with
    `default-features = false, features = ["static_secrets", "zeroize"]`
    (`/home/user/ndarray/crates/encryption/Cargo.toml`) — `getrandom` is NOT
    in that feature list, so this path stays gated off.

  **Confirmed: `EphemeralSecret::random` is still unreachable under kx.rs's
  feature set in 3.0.0.** The constraint that motivated wrapping
  `StaticSecret` instead of using upstream `EphemeralSecret` still holds.

- Minor doc-drift note (not a compile break): kx.rs:16 says upstream
  `random_from_rng` "needs a `rand_core::RngCore + CryptoRng`" (two-trait
  bound, matching the 2.0.1-era rand_core 0.6 design). In 3.0.0 the bound is
  a single trait, `R: CryptoRng + ?Sized` (`x25519.rs:88`), against
  `rand_core = "0.10"`, where `CryptoRng` is a supertrait design over
  `RngCore` rather than a separate bound written out at the call site. The
  practical unreachability conclusion is unchanged, but the doc-comment's
  *phrasing* of the bound would become slightly stale if anyone audits it
  against upstream signatures line-for-line.

## 5. Zeroize behaviour under the `zeroize` feature in 3.0.0

Both `StaticSecret` and `SharedSecret` use the same pattern: a `Drop` impl
that calls `.zeroize()` on the inner `MontgomeryPoint`/`[u8;32]` only under
`#[cfg(feature = "zeroize")]`, plus a marker `ZeroizeOnDrop` impl gated the
same way (this is what lets *downstream* types derive `ZeroizeOnDrop` and
have the compiler check it, without exposing a public no-op `zeroize()` when
the feature is off).

`StaticSecret` (`x25519.rs:271-280`):
```rust
#[cfg(feature = "static_secrets")]
impl Drop for StaticSecret {
    fn drop(&mut self) {
        #[cfg(feature = "zeroize")]
        self.0.zeroize();
    }
}
#[cfg(all(feature = "static_secrets", feature = "zeroize"))]
impl ZeroizeOnDrop for StaticSecret {}
```

`SharedSecret` (`x25519.rs:348-356`):
```rust
impl Drop for SharedSecret {
    fn drop(&mut self) {
        #[cfg(feature = "zeroize")]
        self.0.zeroize();
    }
}
#[cfg(feature = "zeroize")]
impl ZeroizeOnDrop for SharedSecret {}
```

Same shape for `EphemeralSecret` (`x25519.rs:112-120`, unconditional Drop,
gated zeroize body). `encryption`'s `Cargo.toml` enables the `zeroize`
feature, so this matches kx.rs's doc claim at kx.rs:122-126 ("it already
zeroizes on drop ... deliberately has no Debug impl") unchanged.

Feature wiring: `Cargo.toml:57` `zeroize = ["dep:zeroize", "curve25519-dalek/zeroize"]`
— enabling `zeroize` on x25519-dalek 3.0.0 also forwards the feature into
`curve25519-dalek`, same as would be expected in 2.0.1.

No explicit (non-Drop) `impl Zeroize for StaticSecret` or `SharedSecret`
exists in either case — only the Drop-triggered path. `kx.rs` never calls
`.zeroize()` on these types directly (only on its own local `[u8;32]` scalar
buffers via the `zeroize::Zeroize` trait it imports itself, kx.rs:63,
154, 184), so this is consistent either way.

## 6. curve25519-dalek version + SIMD backend auto-selection

- Required version: `curve25519-dalek = { version = "5.0.0", default-features = false }`
  (`/home/user/curve25519-dalek/x25519-dalek/Cargo.toml:41`) — a major bump
  from the current lockfile's 4.1.3.
- Backend selection logic in 5.0.0
  (`/home/user/curve25519-dalek/curve25519-dalek/build.rs`, full file read):
  - `curve25519_dalek_bits` defaults to 64 on any target where
    `CARGO_CFG_TARGET_POINTER_WIDTH == "64"` (`build.rs`
    `deterministic::determine_curve25519_dalek_bits`), independent of arch.
  - Backend defaults (no env override, `build.rs` main "default between
    serial / simd / avx512" branch):
    - If `is_capable_avx512(arch, bits, rustc_version)` — i.e.
      `arch == "x86_64" && bits == Dalek64` AND target features
      `avx512ifma` + `avx512vl` are both present (via
      `CARGO_CFG_TARGET_FEATURE`) AND rustc >= 1.89 (or nightly) — backend
      is `"avx512"` (which *also* stamps `cfg(curve25519_dalek_backend="simd")`
      as a duplicate cfg value, so AVX-512 code gets both cfgs).
    - Else if `is_capable_simd(arch, bits)` — i.e. plain
      `arch == "x86_64" && bits == Dalek64`, **no target-feature check at
      all** — backend is `"simd"`.
    - Else `"serial"`.
  - **Yes: the plain SIMD backend is still auto-selected by default on
    x86_64 (64-bit) in 5.0.0**, exactly as the `is_capable_simd` gate has no
    additional feature requirement beyond arch+bits. The AVX-512 tier is new
    *additional* logic layered on top (needs `avx512ifma`/`avx512vl` target
    features, which are not on by default without `-C target-cpu=...`
    tuning) — it does not change the fact that the baseline "simd" backend
    still wins by default over "serial" on x86_64.
  - I could not diff this against the actual 4.1.3 `build.rs` (not present
    on disk anywhere under `/home/user` — only the 5.0.0 fork tree exists
    locally); **unverified** whether the AVX-512 tier is new in 5.0.0 or
    already existed in 4.1.3. What's verified directly from the file read
    is only 5.0.0's current logic, reported above.

## Silent breaks — compiles fine, behaves differently or needs new attention

1. **`rand_core` becomes a mandatory (non-optional) transitive dependency**
   of x25519-dalek at version `"0.10"` (`Cargo.toml:42`, no
   `optional = true` flag — contrast with `getrandom`/`serde`/`zeroize`
   immediately below it, which are all marked optional). This resolves
   silently today since `encryption` doesn't otherwise touch `rand_core`,
   but it is now unconditionally in the dependency graph and lockfile
   regardless of which x25519-dalek features are on.
2. **`getrandom` version mismatch if ever turned on**: x25519-dalek 3.0.0's
   optional `getrandom` feature pulls `getrandom = "0.4"`
   (`Cargo.toml:44`), a different major version from the `getrandom = "0.2"`
   already depended on directly by `encryption`
   (`/home/user/ndarray/crates/encryption/Cargo.toml`, and used with the
   `js` feature under wasm32). Not exercised today (kx.rs's feature list
   omits `getrandom`), but a landmine for any future contributor who
   flips that feature on expecting one `getrandom` in the tree.
3. **`edition = "2024"`, `rust-version = "1.85"`** for the fork
   (`Cargo.toml:8,32`) vs. unverified edition/MSRV of the 2.0.1
   crates.io release. `encryption`'s own `rust-version = "1.95"`
   comfortably covers this, so not a practical blocker, but the ndarray
   workspace's own top-level `CLAUDE.md` states "Rust 1.94 Stable only" —
   worth a cross-check that 1.94 still satisfies 1.85 MSRV (it does,
   1.94 > 1.85) before assuming zero friction.
4. **`precomputed-tables` is off** under kx.rs's exact feature list
   (`default-features = false, features = ["static_secrets", "zeroize"]`
   omits it, and it's part of x25519-dalek 3.0.0's *default* features
   `["precomputed-tables", "zeroize"]`, `Cargo.toml:56`) — this was
   presumably already the case at 2.0.1 since the crate opts out of
   defaults the same way, so likely not a *new* break, but flagging
   because `EdwardsPoint::mul_base_clamped` (used by
   `PublicKey::from(&StaticSecret)`, `x25519.rs:258`, and by
   `EphemeralSecret`'s own `From` impl at `x25519.rs:108`) will use
   whatever non-table-lookup scalar-mult path curve25519-dalek 5.0.0
   provides instead — a performance-only concern (unverified whether
   the runtime cost differs materially from 4.1.3's non-table path),
   not a correctness break.
5. **`#![no_std]`** crate-level attribute in 3.0.0 (`lib.rs:17`) — unverified
   whether 2.0.1 was already `no_std`; if it wasn't, this is new and
   irrelevant to `kx.rs` (which is compiled for a `std` target and itself
   uses `std::error::Error`, kx.rs:92, on its own `KxError` type, not on
   anything from `x25519_dalek`), so no compile impact either way.
6. **Doc-comment staleness** (see §3 above) — kx.rs's own module doc
   describes the upstream `random_from_rng` bound as
   "`rand_core::RngCore + CryptoRng`"; 3.0.0's actual bound is the single
   trait `CryptoRng: RngCore`-style bound (`R: CryptoRng + ?Sized`,
   `x25519.rs:88`). Purely cosmetic/doc-accuracy, zero functional effect
   since kx.rs never instantiates this generic.
